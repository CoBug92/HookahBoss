# HookahBoss release checklist

Evidence-backed handoff for a future release. This document does not authorize deployment and contains no production credentials or assumed domains.

| Gate | Owner | Required input / action | Validation evidence or command | Priority |
|---|---|---|---|---|
| Final product identity | User + iOS developer | Choose final app name, permanent reverse-DNS bundle ID and supply the final App Store icon set. Update `PRODUCT_BUNDLE_IDENTIFIER`, display name and signing records together. | `xcodebuild -project HookahBoss.xcodeproj -scheme HookahBoss -showBuildSettings`; inspect the archived `.app` Info.plist and icon validation in Organizer. Current `com.hookahboss.app` is provisional and no final icon decision exists. | **Blocking** |
| Distribution and tobacco-policy decision | User | Decide App Store/public versus another permitted distribution route. If App Store is used, keep positioning informational/catalogue-only, with no sales links or encouragement, and accept that review approval cannot be guaranteed under Guideline 1.4.3. | Review the final binary, screenshots, description and keywords against the distribution decision and [App Review Guideline 1.4.3](https://developer.apple.com/app-store/review/guidelines/#physical-harm). `PRODUCT.md` records this unresolved risk. | **Blocking** |
| Honest age rating | User | Complete App Store Connect age-rating answers truthfully, including frequent tobacco references; do not infer the rating from the in-app 18+ gate alone. | Save/export the completed App Store Connect questionnaire and compare it with the 18+ product positioning in `PRODUCT.md`. | **Blocking for App Store** |
| Apple Developer signing and Sign in with Apple | User + iOS developer | Provide/select Apple Developer Team, register the final App ID/bundle ID, enable Sign in with Apple, create the required Service/App identifiers and signing profiles. No private keys belong in git. | `HookahBoss/HookahBoss.entitlements` and `CODE_SIGN_ENTITLEMENTS` already declare the capability. Validate a signed archive and perform Sign in with Apple on a physical device using the production identifiers. | **Blocking** |
| Backend Apple audience | Backend developer + user | Set production `APPLE_CLIENT_ID` or `APPLE_CLIENT_IDS` to the exact approved Apple audiences matching the chosen native/service identifiers. | Start production-configured API with empty/incorrect IDs and confirm fail-closed; run a real `/v1/auth/apple` exchange. Automated issuer/audience/signature/JWKS tests are in `backend/test/auth-core.test.ts`. | **Blocking** |
| Admin allowlist | User / operator | Supply only intended Apple subject identifiers through `ADMIN_APPLE_SUBJECTS`; keep empty to deny all until verified. Treat subjects as sensitive account identifiers. | Sign in with one allowlisted and one ordinary production/staging account; verify `/v1/me/admin-capabilities` grants only the former and admin routes return 403 for the latter. Existing backend tests cover 401/403 policy. | **Blocking if Admin is required at launch** |
| Apple provider token lifecycle smoke | User + backend developer | Supply Apple Team ID, Key ID, `.p8` key, explicit provider client ID included in `APPLE_CLIENT_IDS`, and a versioned AES keyring plus active version through the production secret manager. Retain old decryption keys during rotation. | On staging, exercise first/repeat login and Delete Account; verify Apple exchange/revoke, old-envelope decryption after rotation, server deletion and session invalidation without token logs. Local evidence: migration `008`, `appleProvider.ts`, `apple-provider.test.ts`. | **Blocking** |
| VDS DNS and TLS | Operator | Provide the chosen API hostname, DNS records and a valid automatically renewable TLS certificate; expose only required ports. | From outside the VDS: `curl -fsS https://<api-host>/health`; inspect certificate hostname, chain and expiry. Do not use a placeholder host in build settings. | **Blocking** |
| Production PostgreSQL and backups | Operator + backend developer | Provision an isolated database/user with unique credentials. Define encrypted backup storage, retention, monitoring and a restore drill before importing data. | Record a successful backup and restore into a disposable database; verify restored schema/catalog counts. Docker Compose checked-in credentials are explicitly development-only. | **Blocking** |
| Production migrations and seeds | Backend developer | Apply all migrations in order, then idempotent catalog, mix and article importers. Take a backup before future production migrations. | In `backend`: `npm run migrate`, `npm run seed:catalog`, `npm run seed:mixes`, `npm run seed:articles`; repeat seed imports and confirm counts remain 294 products, 46 mixes and 10 articles. Run `npm run check` first. | **Blocking** |
| Provenance source health | Content owner + backend developer | Periodically rerun source verification; do not advance `verifiedAt` from reachability alone. | Latest live report: 64/64 valid, including 34 semantically verified MUSTHAVE pages and 30 explicitly reachability-only sources; CLI exited zero. Evidence: `backend/reports/provenance-sources-live-2026-09-10-blackburn.json`. Backend suite: 86/86. | **Recommended recurring check; current gate passed** |
| Production environment secrets | Operator | Supply production `DATABASE_URL`, strong random `SESSION_TOKEN_SECRET`, Apple client IDs and admin allowlist through the VDS secret mechanism. Override every dev default; restrict access and define rotation. | Compare deployed environment variable names with `backend/.env.example` without printing values. Confirm startup fails with missing/weak auth configuration. Never copy Docker Compose dev password/secret to production. | **Blocking** |
| Release API URL | iOS developer + operator | Set `HOOKAHBOSS_RELEASE_API_BASE_URL` at Release build time to the real HTTPS API origin. | `xcodebuild ... -configuration Release -showBuildSettings | rg 'API_BASE_URL'`; after archive, `plutil -extract API_BASE_URL raw <archive-app>/Info.plist`. `AppConfigBundleTests` proves missing/non-HTTPS Release values fail closed. | **Blocking** |
| Staging end-to-end smoke | QA + developers | Deploy the same schema/config shape to staging; use non-production Apple/test accounts and representative seeded content. Test anonymous catalogue/articles, authentication, refresh/logout, favorite/rating/inventory/private and personal mix sync, deletion and admin grant/CRUD. | `curl -fsS https://<staging-api-host>/health`; RU/EN HTTP smoke for products/mixes/articles; run iOS smoke on a build pointed at staging and verify server-side state after relaunch. | **Blocking** |
| Device accessibility and visual matrix | QA | On supported iPhones test RU/EN, system light/dark, VoiceOver and the largest practical Dynamic Type sizes. Check cards, sheets, filter/results, article reader, Create and My; verify controls remain visible and hittable. | Automated baseline: 67/67 unit tests (`/private/tmp/hb-blackburn-unit/Logs/Test/Test-HookahBoss-2026.09.10_05-51-05-+0300.xcresult`) and one combined 4/4 XCUITest suite (`/private/tmp/hb-ui-dynamic-full/Logs/Test/Test-HookahBoss-2026.09.10_04-59-12-+0300.xcresult`) covering age EN, EN light, RU dark and EN accessibility XXXL. Attach device screenshots and a VoiceOver checklist for the release candidate. | **Blocking** |
| Privacy manifest and privacy disclosures | User + iOS developer | Reconfirm actual collection before submission. Current implementation declares linked User ID, Other User Content and Product Interaction for app functionality, no tracking; it does not declare email/name. Complete matching App Store privacy answers and provide a privacy-policy URL if required. | `HookahBoss/PrivacyInfo.xcprivacy`; `PrivacyManifestTests` validates keys and bundle inclusion. Inspect the final archive because third-party dependencies may add manifests/categories later. | **Blocking for App Store** |
| App Store metadata | User | Supply localized RU/EN title/subtitle/description, screenshots, support contact/URL, privacy-policy URL and review notes explaining anonymous browsing, Sign in with Apple, account deletion and the informational 18+ scope. Do not include purchase claims or unsupported safety claims. | Two-person review of App Store Connect metadata against the shipped binary and `PRODUCT.md`; verify review credentials/instructions without placing them in the repository. | **Blocking for App Store** |

## Final technical evidence

- Backend: `cd backend && npm run check`
- Content: `npm run seed:validate`, `npm run seed:mixes:validate`, `npm run seed:articles:validate`
- Project generation: `xcodegen generate`
- iOS tests: run `xcodebuild ... test` against the release-candidate commit and retain the `.xcresult`.
- Archive: use Release configuration with the explicit HTTPS API setting and production signing; validate in Xcode Organizer before upload.
